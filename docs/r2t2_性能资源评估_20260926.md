# R2T2 翻译整套流程 性能与资源占用评估

> 评估对象：`confucius4_r2t2`（Qwen3-ASR 微调，离线 ASR + 词级时间戳）配合 `Qwen3-ForcedAligner-0.6B` 对齐模型，落地为「拖拽媒体 → SRT 字幕」的整套流程。
> 硬件：**RTX 5070 Ti Laptop (12GB)** + CUDA 12.8 + Blackwell sm_120a。
> 实测日期：2026-09-26。方法：CLI `--metrics` 官方计时 + 独立进程采样峰值显存/内存。

---

## 1. 流程分解

整套「生成字幕」流水线共 4 个阶段（见 `scripts/r2t2_subtitle.bat` + `words_to_srt.py`）：

```
媒体文件(mp3/mp4/wav)
   │  ① ffmpeg 转码  ──  -ac 1 -ar 16000 -c:a pcm_s16le（成 16k 单声道 PCM wav）
   ▼
WAV(16k 单声道)
   │  ② R2T2 离线 ASR（30s 硬切块，逐块独立 greedy 解码）
   ▼
文本
   │  ③ Qwen3-ForcedAligner-0.6B 词级对齐（非自回归 slot-filling，80ms/帧）→ word_timestamps
   ▼
words.json [{start_sample,end_sample,word,confidence}]
   │  ④ words_to_srt.py（词间 gap>350ms 断行 + CJK 无缝拼接）→ UTF-8 BOM SRT
   ▼
源名.srt（与媒体同目录）
```

### 代码路径关键点（已核验源码）
- **离线长音频**：`session.cpp` `run()` 用 `kOfflineChunkSeconds=30.0` 整段硬切块，每块独立 `run_single`（frontend 提 mel → audio_encoder 编码 → thinker greedy 生成 → 可选 aligner）。**块间无 VAD、无重叠、无上下文续传**（只有固定 context+language 提示）。末块不满 30s 时 graph 重建。
- **图复用（实测确认，修正版）**：offline 默认路径下 `audio-encoder.encode()` 的 `graph_->matches(frames,...)` 与 thinker 的 `prefill_graph->matches(prompt_steps,injection.tokens)`、`decode_graph->can_run(required_cache_steps)` 在**恒定 30s 完整块之间均命中缓存而复用**——只有**不满 30s 的末块**（frames/prompt_steps 变化）才触发重建。实测佐证：418s/14 块 RTF=0.052、3 文件 batch 中 60s(demo_a,2 块) 与 28s/8s 合计仅出现块级 CUDA graph warmup，未见逐块重建开销。→ **上一版"thinker 每 chunk 重建、需改 reuse_graphs=true"的 P0 判断已被证伪**；streaming 的 `generate_reusing_graphs` 用的是另一套 QwenCausalDecodeRuntime（capacity 桶成长 + LSP 前缀续传），其价值在 KV 缓存设备端成长与连续音频前缀续传，而非离线 30s 块的图复用。
- **aligner 串行加载**：R2T2 (~2.5GB 权重+图) 与 aligner (~1.1GB) 无法同驻 12GB 卡，`session.cpp` 构造时 `#release_storage` 释放 R2T2 后再由子会话加载 aligner。
- **对齐触发**：仅当 `return_timestamps=true` 且（请求或检测出）语言非空且文本有可对齐词时，每个 30s chunk 都会 prepare+run 一次 aligner。

## 2. 实测结果（RTX 5070 Ti 12GB / CUDA 12.8）

### 2.1 耗时 / RTF（实时倍率）

| 音频 | 时长 | 语言 | 时间戳 | wall(含时间戳) | RTF | ×实时 |
|---|---|---:|---|---:|---:|---:|
| demo_16k.wav | 14.1s | 自动→英 | ✓ | 0.74s | 0.053 | **18.9×** |
| d_ja.wav（真实日语音频） | 8.3s | 日 | ✓ | 0.53s | 0.064 | **15.6×** |
| four_speaker_short.wav | 28.0s | 英(自动) | ✓ | 4.27s | 0.152 | 6.6× |
| speech 前60s | 60.0s | 英 | ✓ | 2.83s | 0.047 | **21.2×** |
| long_327s.wav | 327.6s | 英 | ✓ | 15.6s | 0.048 | **21.0×** |
| speech_418s.wav | 418.1s | 英 | ✓ | 21.7s | 0.052 | **19.3×** |
| speech_418s.wav | 418.1s | 英 | 无 | 20.0s | 0.048 | 21.0× |

**aligner 额外开销**（同为 418s 英文）：时间戳版 21.7s vs 纯 ASR 20.0s，**Δ≈1.7s ≈ +8.6%**。aligner 本身非自回归极快（每个 30s chunk <2s）。

**真实影片锚点**（9-24 历史实测，`dvdms-090.mp3`）：14665s 日文 AV 音轨、489 个 30s 块、逐块离线转录全程 ≈50 分钟 → **RTF≈0.20（约 5×实时）**。比卡通/干净语音慢，属真实语音密度下的保守上界。

### 2.2 峰值资源占用（进程级实测）

| 输入 | 峰值显存增量(Δ) | 峰值进程内存(WS) | 说明 |
|---|---:|---:|---|
| 8-14s 短音频 | **≈4.2-4.4 GB** | **≈3.6-3.9 GB** | R2T2 加载峰值 |
| 28s / 327s / 418s | **≈4.9-5.7 GB** | **≈3.5-3.9 GB** | 占比：权重(R2T2 q8≈2.3GB + aligner q8≈1.1GB，串行) + CUDA graph + KV cache + 计算图缓冲 |

- **12GB 卡完全够用**：峰值显存占用约一半（4.2-5.7/12.2GB），未触顶；aligner 与 R2T2 串行切换因此没有峰值叠加。
- 进程常驻内存 ~3.5-3.9GB（含 ggml 上下文、CUDA 上下文、模型 mmap）。
- 模型加载本身每次约 **7-9s**（两次 GPU 读文件 + CUDA graph warmup），对短文件是主要墙钟开销。

### 2.3 关键词（客观约束）
- 总墙钟 ≈ **模型加载(7-9s) + 音频时长/RTF + 转码**（转码极快，327s 音频 ffmpeg <0.1s）。
- RTF 波动（6.6×~21×）主要来自**内容本身**（语音密度、解码 token 数、自动语言检测一次开销），与音频长度相关性弱；demo/speech 类干净语音普遍 18-21×，多说话人/真实音轨降到 5-7×。

## 3. 已有优化点（按收益排序，附优先级）

### 🟢 P0 — 已实测、已落地（本次实施交付）

**1. ✅ 批量一次加载（已实施：`scripts/r2t2_subtitle_batch.bat`）**
- 现状（修复前）：旧 `r2t2_subtitle.bat` 每处理一个文件**重新起 CLI 子进程 = 重新加载模型 7-9s**。拖 N 个文件就有 (N-1)×7-9s 纯加载墙钟。
- 收益（实测 3 文件）：单进程 `--batch-audio-dir` 只加载一次 → 3 文件总墙钟 **15.9s**（含 1 次加载 ~10s + 处理 5.8s），对比按文件重启约 38s，**省 ~22s（≈-55%），且文件越多收益越大**。词级 words 按源 stem 分别落盘，逐个转 `.srt` 放回各自媒体目录。
- 改动面：几乎零——复用 CLI 内置 `--batch-audio-dir`（同进程 session 复用），仅改 .bat；无 C++ 代码改动，已用 3 文件端到端回归（英文/日文 SRT 均正确、UTF-8 BOM）。

**2. 离线图复用（⚠️ 已证伪，无需改动）**
- 上一版基于源码表象判断"thinker 每 chunk 重建 prefill/decode 图、需传 reuse 标志"，**实测证明为误判**：恒定 30s 块之间 encoder/thinker 图均已由 `matches`/`can_run`/`frames==frames` 命中复用，末块才重建。长音频 RTF 已到 19-21×，无额外可榨取的图复用空间，故**不做 code 改动**（避免无收益且有回归风险的改动）。

### 🟡 P1 — 质量+速度双收益

**3. VAD 感知切块（已实现 opt-in，但实测不推荐默认启用）**
- 已落地：`confucius4_r2t2` 会话现支持 `--request-option audio_chunk_mode=vad`（Silero VAD `plan_vad_audio_chunks` 替代 30s 硬切，懒加载 VAD 会话，`confucius4_r2t2.vad_model_path` 可选覆盖，默认 `assets/framework/models/silero_vad`）。**默认路径完全不变**，VAD 仅显式开启。
- **实测结论（负收益，勿默认启用）**：真实日文影片 120s——① **漏丢失开头语音段**（fixed 识别出 t=9.2s 起的"まあお互い…"，VAD 首块却从 t=14.84s 开始，9-13s 内容丢失）；② **词级时间戳失真**（VAD 块边界无对齐上下文，长句被压成 ~0.16s 的粗糙 span）；③ **更慢**（14.4s vs fixed 7.5s，含 VAD 推理 + 更多小块固定开销）。合成"语音-8s静音-语音"场景 VAD 与 fixed 无差异。
- 根因：VAD 对 **CTC 纯转录**（parakeet/granite）有跳过静音的收益，但 **R2T2 每个 span 都要 forced aligner 出词级时间戳**——切开短 span 反而破坏对齐、跳过静音会丢上下文。结论：**保留实验性接口但默认关闭**；若要用需大改 aligner 上下文/padding 策略，属深层改动，当前不推。

**4. 长音频 stream-块上下文传递（块间热启动）**
- 现状：块间完全独立，无前块文本/音频作为提示，块首存在冷启动（语言检测、prompt build、前几帧编码）。
- 收益：把 streaming 的稳定前缀机制用于块循环，块首转录质量与速度双提升。

**5. aligner 避免跨 chunk 重复 prepare**
- 现状：`run_single` 内 `forced_aligner_session_->prepare()` 每个 chunk 触发；aligner 会话首块加载后应持续复用；批量路径（同 session）下本已复用，单文件路径每次 `run()` 前构造可能重复初始化。
- 收益：中。批量脚本已天然避免（同 session），纯防御性优化，可放缓。

### 🟢 P2 — 资源/健壮性

**6. 短音频场景缓存模型加载**（已被 P0-1 批量一次加载覆盖）；**7. 显存上限守卫**：12GB 卡已验证够，但若同卡并行需提示 aligner 退 CPU（显存归零）；**8. `confidence` 字段恒 0** 已知不影响时间戳，无需投入。

---

## 4. 结论

- **速度**：R2T2 离线 ASR + 时间戳在 5070 Ti 上 **RTF 0.05-0.20，即约 5-21× 实时**；干净语音普遍 19-21×，真实音轨 5× 起。4 小时影片约需 45-55 分钟（含加载）。
- **资源**：峰值显存约 **5.7GB（50%）**、进程内存 **3.9GB**，12GB 卡余量充足；aligner 串行加载无峰值叠加。
- **当前主要墙钟浪费（修正后）**：每文件重复模型加载(7-9s)。这部分已用 `--batch-audio-dir` 批量脚本消灭（P0 已落地，实测 3 文件 -55%）；离线 30s 块的 thinker 图重建**实测不存在**（末块除外），无额外优化空间。
